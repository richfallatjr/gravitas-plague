Why the Current Crash Is Serious
Metal validation is catching MLX encoding a nil bytes pointer:

  setBytes:length:attributeStride:atIndex:
  bytes argument cannot be nil

That usually means the framework attempted to encode an empty/invalid host-side buffer, invalid scalar argument, or malformed tensor-derived argument into a compute pipeline. The app cannot catch this from outside the package because the assertion aborts the process.

Likely Root Cause Areas
These should be investigated in order.

1. mlx-audio-swift Qwen3TTS generation path is not canaried on visionOS for this exact tuple.

   The README documents the model, but the device proves load succeeds and generate aborts. Treat this as a model/package/device canary failure until the exact MLX operation is isolated.

2. Qwen3TTS sampleToken / suppress-token path.

   In the pinned package, Qwen3TTS.sampleToken always applies suppress-token logic before sampling. Even with package defaults, nil voice, and nil refs, this path is still active.

   The suspect operation is around code shaped like:

     let suppressArr = MLXArray(suppress.map { Int32($0) }).reshaped(1, -1)
     let negInf = MLXArray.full(
         [1, suppress.count],
         values: MLXArray(-Float.infinity),
         dtype: logitsSlice.dtype
     )
     logitsSlice = putAlong(
         logitsSlice,
         suppressArr,
         values: negInf,
         axis: -1
     )

   If `suppress` is empty, malformed, wrong dtype, or contains out-of-range token IDs, this could plausibly reach an invalid Metal argument. The package needs instrumentation before this operation.

3. Prompt preparation shapes.

   Qwen3TTS prompt preparation slices token embeddings with assumptions about minimum token count and special-token layout. The README text should be valid, but the canary must log actual token count, embedding shape, and every slice bound before the first talker forward pass.

4. Quantized 8-bit op compatibility.

   The previous 4-bit model asserted. The current 0.6B 8-bit model also asserts during generate. That points either to a shared Qwen generation operation or to quantized-kernel compatibility on this device/OS/package combination.

5. Staged writable model cache.

   The app stages the bundled model to:

     Library/Caches/TuringWritableModels/qwen3-tts-12hz-0.6b-base-8bit-50f45ef0047cde7e84c2ef04326acb8ada2436a7

   This exists because the package may need a writable tokenizer/model directory. The cache must be keyed by model revision, tokenizer revision, package revision, app build, and runtime schema. If any of those change, the staged directory must be purged and rebuilt.

6. Package revision mismatch.

   The app is pinned to a specific `mlx-audio-swift` main revision. The architect should test whether a newer package revision fixes Qwen3TTS on visionOS, but only after creating a canary that records exact package revisions.

Non-Fixes
Do not spend more time on these as primary fixes:

1. Adding refText.
   In this package, refText belongs to reference conditioning when refAudio is also present. Phase 0 is Base smoke and must keep refAudio/refText nil.

2. Reintroducing Ryan/Aiden.
   The current nil voice path still asserts. Named voices are a later canary variant, not the base fix.

3. Disabling Metal API Validation.
   That would hide the invalid encode. It would not prove generated audio is correct.

4. Adding catch/retry around model.generate.
   The process aborts before Swift can recover.

5. Falling back to system TTS, prerecorded audio, Python, PyTorch, or CPU.
   Phase 0 is explicitly Swift + MLX + local model + GPU.

Robust Fix Architecture
The architect should stop treating the app wrapper as the diagnostic surface. The app has narrowed the request to the minimal documented Base call. The next layer is package/model canary and instrumentation.

Required robust path:

1. Make Story runtime refuse to call Qwen unless a native canary has passed for this exact tuple:

   - model ID

   - tokenizer revision
   - mlx-audio-swift revision

2. Keep the debug button explicit:

   - "Run Qwen Canary" may crash while this is unresolved.
   - "Generate + Play Qwen Line" should remain disabled unless the canary passed.

3. Persist a crash breadcrumb before every native canary stage.

   Because a Metal assert kills the process, the app cannot write a normal failure report after the crash. It must write `lastStartedStage` before each stage and clear/update it only after the stage completes. On next launch, if a previous run died with an uncleared stage, the app can report:

4. Locally patch or fork mlx-audio-swift for diagnostics.

      target: MLXArray,
      indices: MLXArray,

      stage: String
