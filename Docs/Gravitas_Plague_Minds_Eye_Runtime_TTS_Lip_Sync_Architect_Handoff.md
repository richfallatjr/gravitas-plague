## 2. Required user experience

### Product-owner locked objectives

The implementation must hit these objectives:

1. Generate real speech-derived lip keyframes for Turing TTS on Vision Pro at
   runtime. The production result must be phoneme/viseme aligned, not merely an
   amplitude-driven open/close flap.
2. Analyze the exact final PCM for each short TTS segment, together with the exact
   text used to synthesize that segment whenever available.
3. Submit analysis immediately as each individual segment finishes synthesis and
   postprocessing. Do not wait for the entire multi-segment response to finish.
4. Exploit the time Turing already spends generating later segments: lip-sync work
   for completed segments should overlap continued TTS generation and the existing
   playback queue.
5. Budget approximately 1–2 seconds of runtime lip-sync computation per short
   segment if that produces authored-quality keyframes. A 40 ms heuristic deadline
   is not the product target.
6. Make a ready track available before its segment becomes audible whenever the
   natural generation/playback buffer permits. If a track is still late, start
   audio on schedule, keep the portrait visible at rest, and join at the correct
   elapsed frame when the track arrives.
7. Keep the existing amplitude/zero-crossing “flapping” analyzer only as explicit
   emergency degradation. It must not be presented as the completed runtime
   lip-sync implementation.
8. Prove real per-segment latency and incremental peak memory while Qwen and Mind’s
   Eye are resident. The segments are expected to be short, but the design must
   measure their actual distribution instead of assuming every segment fits.

One Turing response must look and sound like one uninterrupted remote presence:

```text
authored Big Mike PR is visible and still playing
  -> Turing begins computing the response
  -> the same card remains visible at rest with selfie motion and blinking
  -> filler, if any, uses its authored filler cues
  -> the first generated TTS segment starts
  -> generated semantic mouth poses follow the actual generated speech
  -> silent gaps return to rest without hiding or rebuilding the card
  -> later filler/generated segments reuse the same card and motion session
  -> response completion removes the card once
```

The current failure is more basic than mouth accuracy: the visible authored card
is destroyed when Qwen preflight begins because the authored parent-flow run ID
does not equal the child generated-response run ID. That continuity defect and the
runtime mouth-manifest producer belong in the same implementation directive.

Hard product rules:

- Audio and story progression always win. Lip-sync work must never block, cancel,
  truncate, or add an unbounded delay to TTS playback. The natural segment queue
  may absorb the 1–2 second analysis target, but the runtime must not stall audible
  playback after its scheduled/reveal-ready start merely to wait for keyframes.
- Keep the correct actual speaker. Never substitute Big Mike for Rich, Dad,
  Broadcaster, Cat Eye 81, or an unavailable speaker package.
- Keep one Mind’s Eye card, one current vignette package, one compositor output,
  and one mouth-playback owner.
- Do not hide, dispose, rebuild, or restart the motion seed merely because the
  response changes among an authored PR, Qwen compute, filler, silence, and
  generated clips.
- While no mouth track is ready, keep the visible portrait alive at `rest` with
  normal floaty motion and blinking.
- A late mouth track may join an already audible clip at the correct elapsed
  frame. It must not restart either audio or animation from frame zero.
- Mouth poses select only among the five semantic families already shipped:
  `rest`, `small`, `wide`, `round`, and `teeth`.
- The runtime aligner must never name or load PNGs. Existing Mind’s Eye packages
  preload the art, and the existing variant planner selects among multiple images
  within a semantic pose family.
- Do not copy audio, art, model files, or manifests into character folders as a
  shortcut. Do not create permanent generated manifests in the app bundle.
- Generated manifests are transient runtime data. Diagnostic persistence may be
  available only behind a qualification/debug flag and must be excluded from
  production Release behavior.
- All expensive analysis must run off the main actor with explicit serialization,
  cancellation, memory bounds, and stale-result rejection.
- Preserve explicit critical-memory safety. Do not retain a full package through
  genuinely unsafe pressure without measuring it and defining a safe downgrade.

## 7. Runtime mouth-generator architecture to specify

### 7.1 Input contract

For each fully postprocessed generated segment, the runtime generator needs:

```swift
struct RuntimeLipSyncInput: Sendable {
    let responseRunID: UUID
    let segmentIndex: Int
    let speaker: TuringSpeaker
    let exactSourceText: String?
    let interleavedPCM: [Float]
    let sampleRate: Int
    let channelCount: Int
    let sampleCountPerChannel: Int
}
```

Use repository-native identity types rather than duplicating these example fields.
The final contract must make it impossible to attach a result to a different run,
segment, speaker, or processed waveform.

`exactSourceText` is the text handed to Qwen for that segment, not a later display
string or a reconstructed transcript. Preserve punctuation and token order. If
the selected runtime method needs normalized phonemes, normalization belongs
inside the generator and must not mutate the authoritative source text.

Use the actual postprocessed PCM that will be played. Do not analyze pre-trimmed or
pre-normalized audio and then assume the timing remains registered.

### 7.2 Output contract

The output is semantic and sparse. It must not reference image filenames:

```swift
struct RuntimeLipSyncManifest: Sendable {
    let schemaVersion: Int
    let sampleRate: Int
    let sampleCount: Int
    let framesPerSecond: Int // exactly 60
    let poseRuns: [MouthPoseRun]
}

struct MouthPoseRun: Sendable {
    let startFrame: Int
    let endFrameExclusive: Int
    let pose: MouthPose // rest, small, wide, round, teeth
}
```

Every accepted manifest must satisfy:

- schema and rate are supported;
- sample rate and sample count match the analyzed playback PCM exactly;
- frame count is derived using the repository’s canonical duration math;
- the first run starts at frame zero;
- runs are ordered, contiguous, nonempty, and cover the full frame count;
- the last run ends at `frameCount`;
- adjacent runs do not repeat the same pose;
- only the five supported semantic poses occur;
- values are finite and integer bounds cannot overflow;
- a manifest that fails any check is discarded atomically.

If the architecture serializes manifests for diagnostics or tests, use stable pose
names rather than relying on internal enum bit values. Production playback should
consume the in-memory validated representation without writing and rereading JSON.

### 7.3 Engine selection

Select and fully specify a runtime-capable technique whose production output is
speech-aligned keyframes rather than loudness flapping. Because the exact TTS text
is available, prefer a technique that uses text and final audio together unless
measurement proves another method is more accurate and cheaper. Evaluate at least:

1. text-plus-audio phoneme forced alignment using the exact segment transcript;
2. a lightweight audio-to-phoneme/viseme Core ML or native inference model;
3. synthesis metadata or token timing that Qwen can expose without a second model;
4. a measured hybrid that aligns text coarsely and uses acoustic boundaries for
   onset/offset refinement.

The final directive must choose one production path. It must not tell Codex to
“pick a library.” Document:

- source and exact pinned version;
- license and redistribution implications;
- Vision Pro/visionOS and arm64 compatibility;
- whether it requires C/C++, Core ML, Metal, Accelerate, or another runtime;
- model/resource size in the built app and thinned app;
- initialization cost and whether initialization is lazy;
- peak and steady memory while Qwen is resident;
- expected latency for the repository’s real short-segment distribution;
- cancellation granularity and thread-safety;
- deterministic output requirements;
- offline/no-network operation;
- how the dependency is built, signed, and included in Xcode.

Do not propose Montreal Forced Aligner, ffmpeg, Python, a subprocess, or a host CLI
as the device runtime. Those are valid authoring tools, not a shippable visionOS
runtime architecture.

If exact alignment cannot reliably finish before playback, the design must still
support late delivery. It may also emit a fast provisional track and later replace
it only if replacement can be proven not to cause visual discontinuity. A simple
and safe first production design is usually one final late-join track plus rest or
the existing DSP fallback before it arrives.

### 7.4 Scheduling and deadlines

The current 40 ms hard budget has already failed for every segment under real Qwen
load and is not the product requirement. The product owner explicitly accepts an
approximately 1–2 second analysis budget for each short generated segment when that
time buys accurate lip keyframes. The architect must convert that target into
measured cold/warm deadlines and queue rules rather than another magic constant.

Required properties:

- analysis begins as soon as postprocessed PCM and exact text are available;
- each completed segment is enqueued independently while Qwen continues producing
  later segments;
- analysis is never deferred until the entire response has rendered;
- at most one heavy runtime alignment job runs concurrently unless device evidence
  proves a higher safe bound;
- queue count and queued PCM bytes are bounded;
- audio preparation proceeds independently;
- a short bounded pre-audio visual wait is allowed only if it already fits the
  repository’s reveal policy and never becomes an audio dependency;
- a result arriving after audio start is emitted through the existing late-track
  event and catches up to the current pause-aware clock;
- a result arriving after segment completion, cancellation, response replacement,
  speaker change, reset, shutdown, or stale ticket/handle rejection is dropped;
- all deadlines use monotonic clocks;
- cancellation is checked within the generator, not only before and after it;
- the worker does no main-thread blocking, polling sleep, or `waitUntilCompleted()`.

Specify separate measured budgets for:

```text
cold generator initialization
warm per-segment generation, targeting completion within 1–2 seconds
maximum queued PCM bytes
maximum queued segment count
maximum permitted late-join age
shutdown/cancellation latency
```

## 8. Presentation-continuity architecture

- retaining motion/blink state and output texture;
- changing speaker or surface safely when the actual next audible speaker differs;
- ending once on response completion, cancellation, story reset, app background,

- rejecting stale parent or child completions after a later response wins.

The provisional `.retainActivePresentation` policy fixes the observed identity

High-memory behavior must distinguish:

1. normal Qwen preflight with enough memory: keep/adopt the compatible visual;
2. warning pressure: keep the visible output if safe and avoid new package churn;
3. critical pressure: audio survives and visual degradation is explicit.

If a full source package cannot safely coexist with Qwen, evaluate a measured
frozen-card mode that retains only the visible entity/output surface/last good
frame plus lightweight motion while releasing heavy source textures. This option
is valid only if it is compatible with the existing package/texture ownership and
can restore mouth animation without corruption or duplicate residency. Otherwise
the directive must preserve the current explicit critical-pressure teardown and
log that degradation. Never silently make normal preflight look like critical
pressure.

## 9. Failure policy

Every failure must be contained to visual fidelity:

| Failure | Required behavior |
|---|---|
| No generator installed | Keep card; use bounded existing fallback or rest; play audio |
| Generator cold start is late | Keep card at rest/fallback; late join if still current |
| Invalid manifest | Reject entire manifest; keep card; play audio |
| Runtime model load fails | Disable generator for a bounded scope; keep audio and card |
| Analysis queue full | Drop or fall back according to explicit policy; never block audio |
| Segment is cancelled/stale | Cancel/drop result; never affect current segment |
| Speaker package unavailable | Audio-only continuation; no Big Mike substitution |
| Warning memory pressure | Avoid churn; preserve current presentation if safe |
| Critical memory pressure | Explicit logged visual teardown or qualified frozen mode |
| App inactive/reset/shutdown | Cancel jobs, remove events, release resources exactly once |

No fallback path may perform runtime PNG loading, load a second vignette package,
or allocate a frame-sized CPU image buffer.
