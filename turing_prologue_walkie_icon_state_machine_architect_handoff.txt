PURPOSE

Transition the Prologue from debug-window-driven execution to the physical
Story walkie-talkie without removing the debug window yet.

The initial player-facing entry point is a play icon above the placed walkie.
That icon starts prologue.scriptPoint01. The icon disappears while any Turing
Flow or conversation is computing or playing. When the flow explicitly opens
the microphone gate, the same icon position returns as a microphone icon.

This is a real game entry point. It must not depend on the Story debug window
being open, mounted, or observing notifications.


NON-NEGOTIABLE PLAYER BEHAVIOR

1. Enter Story Mode and select/start the Prologue.
2. Run the existing room scan and place the existing Story props.
3. Once the walkie bundle is placed and the Prologue is armed, show one play
   icon above the walkie at TuringStoryWalkieTalkieIcon_Root.
4. The play icon and the physical walkie are both tappable.
5. The first accepted tap immediately disables both interaction surfaces and
   hides the icon before asynchronous work begins.
6. The accepted tap starts prologue.scriptPoint01 with trigger .userPlay.
7. ScriptPoint01 continues through its existing prerecording, Foundation
   voicePrompt, filler, Fresh2 Qwen generation, and ordered promptVoice
   playback.
8. While any of that work is active, no icon is visible and the physical
   walkie accepts no play or microphone input.
9. Successful completion of ScriptPoint01 promptVoice playback uses its
   existing descriptor gate:
   interactionGateAfterCompletion = microphone.
10. When the gate becomes microphone, show a microphone icon at the same
    anchor. The physical walkie also becomes a hold-to-talk target.
11. Holding either microphone surface starts the existing open-comm and
    dictation path. Releasing sends the existing conversationPrompt, whose
    generated spoken response is conversationVoice.
12. As soon as conversation work begins, hide the icon and disable both
    interaction surfaces.
13. ScriptPoint02 is triggered only after successful completion of the first
    Big Mike conversationVoice playback that follows ScriptPoint01 promptVoice.
    The existing episode controller then schedules ScriptPoint02 and
    automatically advances through ScriptPoint03. The icon remains hidden for
    the entire chain, including configured delays and fixed lead-ins.
14. A normal Turing Flow exposes the microphone after successful promptVoice
    playback. ScriptPoint02 would therefore expose the microphone normally,
    but its automatic continuation to ScriptPoint03 overrides that intermediate
    gate. No microphone icon may flash between ScriptPoint02 and ScriptPoint03.
15. ScriptPoint03 is the terminal point in this chain. Its successful
    promptVoice completion follows the normal rule, returns the gate to
    microphone, and makes the microphone icon reappear.
16. The debug window and its buttons remain available for diagnostics, but it
    is not the owner of physical walkie interaction.


REQUIRED STATE MACHINE

The existing TuringFlowInteractionGateController is the authoritative state.
Do not create a second independent truth for whether play or microphone is
allowed.

Existing states:

  closed
  play
  busy
  microphone

Required visual and input mapping:

  gate closed:
    icon hidden
    play disabled
    microphone disabled
    physical walkie disabled

  gate play:
    play icon visible
    play tap enabled on icon
    play tap enabled on physical walkie
    microphone disabled

  gate busy:
    icon hidden
    play disabled
    microphone disabled
    physical walkie disabled

  gate microphone:
    microphone icon visible
    hold-to-talk enabled on icon
    hold-to-talk enabled on physical walkie
    play disabled

The presentation state can be derived, not stored separately:

```swift
enum TuringStoryWalkiePresentation: Equatable {
    case hidden
    case play
    case microphone

    init(gate: TuringFlowInteractionGateController.State) {
        switch gate {
        case .play:
            self = .play
        case .microphone:
            self = .microphone
        case .closed, .busy:
            self = .hidden
        }
    }
}
```

NORMAL PROMPTVOICE GATE AND AUTOMATIC-ADVANCE OVERRIDE

The default Turing Flow contract is:

```text
successful promptVoice playback completion -> microphone
```

This applies to ScriptPoint01, ScriptPoint03, future standalone ScriptPoints,
and normal Turing Flows for other props and characters.

The only exception in this Prologue chain is an intermediate point that is
about to auto-advance immediately. ScriptPoint02 is such a point. It completes
its promptVoice successfully, but the episode orchestrator suppresses the
otherwise normal microphone transition because ScriptPoint03 is already the
next scheduled action.

Do not hardcode this behavior to the string "prologue.scriptPoint02". Derive it
from progression semantics:

```swift
let suppressMicrophoneForAutomaticAdvance =
    descriptor.progression.automaticAdvance &&
    descriptor.progression.nextScriptPointID != nil

let effectiveCompletionGate:
    TuringFlowDescriptor.Progression.InteractionGate =
        suppressMicrophoneForAutomaticAdvance
        ? .closed
        : .microphone

await TuringFlowInteractionGateController.shared
    .applyCompletionGate(
        effectiveCompletionGate,
        identity: identity
    )
```

For an automatic chain, keeping the state busy instead of publishing closed is
also acceptable if ownership remains correct. The externally observable rule
is strict: hidden and noninteractive from the intermediate point's playback
through the next point's beginFlow. There must be no microphone-state event and
no one-frame microphone icon flash.

Normalize ScriptPoint02's authored completion gate back to the normal semantic
default:

```json
"progression": {
  "nextScriptPointID": "prologue.scriptPoint03",
  "automaticAdvance": true,
  "interactionGateAfterCompletion": "microphone"
}
```

The runtime automatic-advance override suppresses that microphone for this
chain. ScriptPoint03 has no automatic next point, so its successful promptVoice
completion applies microphone normally.

5. ScriptPoint02 waits for successful conversationVoice playback, and
   ScriptPoint03 is its automatic continuation.

Terminology is strict in this handoff:

```text
promptVoice:
  generated voicePrompt speech belonging to a ScriptPoint

conversationVoice:
  generated conversationPrompt response after player dictation
```

ScriptPoint01 promptVoice completion opens the microphone only. It does not
trigger ScriptPoint02. The subsequent conversationVoice must finish
successfully, with every expected generated segment played through actual
playback completion, before ScriptPoint02 is eligible to start.

Current progression:

```text
ScriptPoint01 promptVoice completes successfully
  -> gate microphone
  -> player records and sends a conversation turn to Big Mike
  -> conversationPrompt computes Big Mike conversationVoice
  -> all conversationVoice segments complete actual playback successfully
  -> TuringEpisodeFlowController.conversationPlaybackCompleted
  -> close gate immediately
  -> wait ScriptPoint02 delay
  -> run ScriptPoint02
  -> ScriptPoint02 promptVoice completes
  -> normal microphone result suppressed by automatic-advance override
  -> automatically run ScriptPoint03 without exposing microphone
  -> ScriptPoint03 promptVoice completes
  -> normal completion gate microphone
```

GATE API CHANGES

Add an explicit initial arming operation, an atomic play claim, and a narrowly
scoped failed-claim recovery. Implement these methods inside
TuringFlowInteractionGateController (or in an extension in the same Swift file)
because they use its private state and publish helper.

```swift
@MainActor
extension TuringFlowInteractionGateController {
    func armPlay(reason: String) {
        guard state == .closed else {
            print("""
            [TuringFlowGate] play arm ignored
              state: \(state.rawValue)
              reason: \(reason)
            """)
            return
        }

        state = .play
        ownerFlowInstanceID = nil
        publish(reason: "playArmed.\(reason)")
    }

    func claimPlay(reason: String) -> Bool {
        guard state == .play else {
            print("""
            [TuringFlowGate] play claim ignored
              state: \(state.rawValue)
              reason: \(reason)
            """)
            return false
        }

        // Hide and disable the icon before creating an asynchronous Task.
        state = .busy
        ownerFlowInstanceID = nil
        publish(reason: "playClaimed.\(reason)")
        return true
    }

    func restorePlayAfterFailedClaim(reason: String) {
        guard state == .busy,
              ownerFlowInstanceID == nil else {
            return
        }

        state = .play
        publish(reason: "playClaimFailed.\(reason)")
    }
}
```

The exact implementation may route through a private transition helper, but
claimPlay must be synchronous on MainActor and atomic. Two rapid taps must not
start two ScriptPoint01 runs.

Required readiness handshake:

```swift
func episodeStarted(_ episodeID: TuringEpisodeID) {
    activeEpisodeID = episodeID
    armIfReady(reason: "episodeStarted.\(episodeID.rawValue)")
}

func walkieInstalled(
    iconAnchor: Entity,
    walkieRoot: Entity
) {
    iconController.install(
        iconAnchor: iconAnchor,
        walkieRoot: walkieRoot
    )
    walkieReady = true
    renderGateState(reason: "walkieInstalled")
    armIfReady(reason: "walkieInstalled")

private func armIfReady(reason: String) {
    guard activeEpisodeID == .prologue,
          walkieReady else {
        return
    }
    gate.armPlay(reason: reason)
}
```

This handshake must tolerate command ordering. Episode selection may happen
before or after room placement finishes.

Gate observation:

```swift
private func observeGate() {
    gateObserver = NotificationCenter.default.addObserver(
        forName: .turingFlowInteractionGateChanged,
        object: gate,
        queue: .main
    ) { [weak self] _ in
        Task { @MainActor in
            self?.renderGateState(reason: "gateChanged")
        }
    }
}

private func renderGateState(reason: String) {
    let presentation: TuringStoryPropBillboardIconController.Presentation
    switch gate.state {
    case .play:
        presentation = .play
    case .microphone:
        presentation = .microphone
    case .closed, .busy:
        presentation = .hidden
    }
    iconController.apply(presentation)
}
```

MICROPHONE HOLD ACTION

Move the existing production operations out of TuringEpisodePickerView. The
new controller must call the same existing services:

```text
hold begins
  -> verify gate.microphoneEnabled
  -> set holdActive
  -> TuringWalkieCommsFXController.playOpenCommBeforeRecording
  -> TuringDictationCoordinator.beginHoldToRecord

hold ends
  -> endHoldToSend
  -> playSendCommAndStartSendingLeadIn
  -> TuringBigMikeConversationRunner.run conversationPrompt
  -> TuringFlowConversationRunner sets gate busy immediately
  -> successful actual conversationVoice playback completion drives episode
     progression
```

Production code outline:

```swift
func microphoneHoldBegan(source: String) {
    guard gate.microphoneEnabled,
          holdActive == false else {
        return
    }

    holdActive = true
    Task { [weak self] in
        guard let self else { return }
        await TuringWalkieCommsFXController.shared
            .playOpenCommBeforeRecording(
                reason: "prologueMic.\(source)"
            )
        guard self.holdActive,
              self.gate.microphoneEnabled else {
            await self.dictation.cancel(
                reason: "holdEndedBeforeRecording"
            )
            return
        }
        await self.dictation.beginHoldToRecord()
    }
}

func microphoneHoldEnded(source: String) {
    guard holdActive else { return }
    holdActive = false

    conversationTask = Task { [weak self] in
        guard let self else { return }
        do {
            let transcript = try await self.dictation.endHoldToSend()
            await TuringWalkieCommsFXController.shared
                .playSendCommAndStartSendingLeadIn(
                    reason: "prologueMic.\(source)"
                )
            _ = await TuringBigMikeConversationRunner.run(
                playerDictation: transcript,
                seedStore: .shared,
                onSegmentZeroReady: nil
            )
        } catch {
            await TuringWalkieCommsFXController.shared
                .stopSendingLeadIn(
                    reason: "prologueMicFailed"
                )
            await TuringWalkieCommsFXController.shared
                .stopAmbientWalkieStatic(
                    reason: "prologueMicFailed"
                )
        }
    }
}
```

Preserve the existing HUD event callbacks by injecting a closure from
PlagueDemoSession or PlagueImmersiveCoordinator. Do not require the SwiftUI
debug view to publish them.

FAILURE AND RETRY RULES

1. A rejected duplicate tap does nothing.
2. A stale flow completion cannot change the gate because the existing gate
   checks ownerFlowInstanceID.
3. A ScriptPoint01 startup failure may restore the play affordance, but must not
   automatically rerun the point.
4. A failure after authored prerecording begins continues to follow existing
   Turing Flow failure behavior. Do not cancel valid PR playback.
5. During any failure cleanup, the icon must never show microphone unless the
   authoritative gate is microphone.
6. A room rescan temporarily hides and disables interaction until the new
   walkie anchor is committed.
