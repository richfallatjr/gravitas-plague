Architect Handoff: Native Qwen VoiceDesign Dynamic Codebook Generation

Goal
Make the native in-repo Qwen VoiceDesign path generate audio from the selected
spoken text and voice prompt, instead of decoding the fixed golden codebook
fixture. The immediate show-off target is a full Big Mike broadcast recording.

Current State
- The app has an in-repo native Swift/MLX Qwen runtime:
  Gravitas Plague/Gravitas Plague/Turing/QwenNative

- The Story episode picker button calls:
  Gravitas Plague/Gravitas Plague/Turing/Debug/TuringNativeQwenHelloWorldCanary.swift

- Prompt text and voice instruction are routed into:
  TuringQwenNativeVoiceDesignEngine.generateVoiceDesign(
      text: input.spokenText,
      voiceDescription: input.instruction,
      language: input.language,
      maxNewTokens: 256,
      seed: 0
  )

- The selected long-form text and Big Mike VoiceDesign prompt are now hardcoded
  in:
  Gravitas Plague/Gravitas Plague/Turing/Debug/TuringNativeQwenVoiceDesignCanaryPresets.swift

- The golden fixture text JSON has also been text-replaced in:
  Gravitas Plague/Gravitas Plague/Turing/QwenNative/Reference/Golden/voice_design_big_mike_hello/input.json
  Gravitas Plague/Gravitas Plague/Turing/QwenNative/Reference/Golden/voice_design_big_mike_hello/prompt-strings.json
  Gravitas Plague/Gravitas Plague/Turing/QwenNative/Reference/Golden/voice_design_big_mike_hello/tokenizer-fixture.json

Important: those JSON edits do not regenerate tokenizer IDs, codebook rows, or
reference-output.wav. They only replace the text fields. The real audio is still
controlled by the generated codebook rows.

Root Cause
The runtime is not truly dynamic yet. It gets through prompt building, talker
forward, first codec-token sampling, and one code-predictor row, but then it
short-circuits into a fixed fixture continuation.

Path B: Real Runtime Dynamic Generation
This is the implementation needed for Story Mode dynamic voiceScript.

The current runtime must stop appending TuringQwenNativeCodePredictor.expectedFixtureRows
and instead autoregressively generate codebook rows until stop condition or max
tokens.

Key files:
- TuringQwenNativeVoiceDesignEngine.swift
- TuringQwenNativeCodePredictor.swift
- TuringQwenNativeTalkerForwardRunner.swift
- TuringQwenNativeCodecSampler.swift
- TuringQwenNativeSpeechDecoder.swift
- TuringQwenNativeMemoryControl.swift

Required Runtime Architecture

1. Replace generateFixtureCodebook(...) with generateDynamicCodebook(...).

Target API:

private func generateDynamicCodebook(
    initialFirstCodecToken: Int,
    initialTalkerLastHiddenState: MLXArray,
    promptInputs: TuringQwenNativeTalkerPromptInputs,
    maxNewTokens: Int
) throws -> [[Int]] {
    var rows: [[Int]] = []
    var currentFirstCodecToken = initialFirstCodecToken
    var currentTalkerLastHidden = initialTalkerLastHiddenState

    for step in 0..<maxNewTokens {
        let group = try TuringQwenNativeCodePredictor.generateCodeGroup(
            firstCodecToken: currentFirstCodecToken,
            talkerLastHiddenState: currentTalkerLastHidden,
            config: config,
            tensorIndex: tensorIndex,
            expectedFixtureRowIndex: nil
        )

        rows.append(group.tokenIDs)

        if shouldStopAfterCodeGroup(group.tokenIDs, step: step) {
            break
        }

        let nextInput = try nextTalkerInputEmbedding(
            codeGroup: group.tokenIDs,
            generationStep: step,
            promptInputs: promptInputs
        )

        let next = try TuringQwenNativeTalkerForwardRunner.runOneGeneratedStep(
            inputEmbedding: nextInput,
            previousState: /* KV cache / generation state */,
            config: config,
            tensorIndex: tensorIndex
        )

        currentTalkerLastHidden = next.finalLastHiddenState
        currentFirstCodecToken = try TuringQwenNativeCodecSampler.selectFirstCodecToken(
            logits: next.logits,
            sequenceLength: next.sequenceLength,
            vocabSize: config.talkerConfig.vocabSize
        ).tokenID

        TuringQwenNativeMemoryControl.clearCache(label: "dynamicCodebook.step.\(step)")
    }

    return rows
}

2. Implement one-step talker forward with KV cache.

The existing runtime can do the initial full prompt forward:

TuringQwenNativeTalkerForwardRunner.runFullForward(...)

That is not enough for long generation. Re-running the full graph for every row
will blow memory and time on Vision Pro.

Add:

struct TuringQwenNativeTalkerGenerationState {
    var pastKeyValues: [TuringQwenNativeLayerKV]
    var cachePosition: Int
    var attentionMask: MLXArray
}

struct TuringQwenNativeGeneratedStepOutput {
    let logits: MLXArray
    let finalLastHiddenState: MLXArray
    let sequenceLength: Int
    let state: TuringQwenNativeTalkerGenerationState
}

enum TuringQwenNativeTalkerForwardRunner {
    static func runFullForwardForGenerationState(...) throws
        -> (TuringQwenNativeTalkerForwardOutput, TuringQwenNativeTalkerGenerationState)

    static func runOneGeneratedStep(
        inputEmbedding: MLXArray,
        previousState: TuringQwenNativeTalkerGenerationState,
        config: TuringQwenNativeConfig,
        tensorIndex: TuringQwenNativeSafetensorsIndex
    ) throws -> TuringQwenNativeGeneratedStepOutput
}

The one-step call must:
- Feed exactly one generated embedding: shape [1, 1, hiddenSize].
- Reuse KV cache from the previous talker pass.
- Advance cache position by one.
- Extend attention mask mechanically.
- Return logits for the new position and final last hidden state.

4. Implement correct stop logic.

Do not hardcode seven rows. Stop when official Qwen generation would stop.

Architect should inspect official Qwen source and generation_config.json for:
- EOS token / stop token handling
- suppress tokens
- max_new_tokens
- language tokens
- codebook row format

Initial conservative implementation:

private func shouldStopAfterCodeGroup(
    _ codeGroup: [Int],
    step: Int
) -> Bool {
    if step <= 0 {
        return false
    }

    // Replace with official stop token check once confirmed.
    if let eos = config.talkerConfig.eosTokenID,
       codeGroup.first == eos {
        return true
    }

    return false
}

If config does not expose eosTokenID yet, add it from config.json /
generation_config.json rather than inventing a value.

5. Segment long text for runtime.

Do not try to generate a whole long broadcast as one device runtime segment
unless specifically testing memory. The production Story path should feed short
segments:
- 3-5 second spoken chunks for runtime
- Qwen remains sequential
- playback can start after each generated clip
- next clip computes while current clip plays once memory is stable

For the full show-off recording, either:
- use Path A offline generation, or
- run runtime generation segment-by-segment and concatenate/play in order.

6. Control memory aggressively.

Known memory constraints:
- Previous attempts hit 5 GB and 8 GB high-water failures.
- Speech decoder memory scales with codebook row count.
- Repeated full talker graph evaluation is not acceptable for device runtime.

Rules:
- Load model weights once per canary/session where possible.
- Do not retain all intermediate MLXArray values longer than needed.
- Release per-step arrays after sampling.
- Clear MLX cache after each generated row and after decode.
- Log memory before/after prompt, initial forward, each N rows, decode, playback.
- Keep the increased memory entitlement in place.

Recommended logs:

[TuringQwenNative] dynamic codebook generation started
  textUTF16: ...
  instructUTF16: ...
  maxNewTokens: ...
  fixtureRowsUsed: false

[TuringQwenNative] dynamic codebook row generated
  rowIndex: ...
  firstCodecToken: ...
  tokenIDs: [...]
  memoryMB: ...

[TuringQwenNative] dynamic codebook generation finished
  rowCount: ...
  stopReason: eos|maxTokens|manual
  fixtureRowsUsed: false

Fastest Show-Off Recommendation
For an immediate full voice recording to show off, use Path A first:
- Generate the full broadcast WAV with official Qwen on Mac.
- Verify the WAV audibly speaks the full broadcast in Big Mike style.
- Commit the resulting metadata if useful, but do not ship the WAV as production
  dialogue unless explicitly allowed.

Then implement Path B for real app runtime.

The reason: Path B needs KV-cache-correct one-step talker generation and memory
control. That is the correct final implementation, but it is more than a text
swap. Path A can produce the full recording quickly while Path B is built
properly.
