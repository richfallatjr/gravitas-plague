Gravitas Plague MainActor Architecture Audit
============================================

Purpose
-------
This file is an architect-facing inventory of what is currently connected to the
MainActor, why it is there, and where optimization work should start.

Goal for the next architecture phase:

    Make the MainActor a thin shell that owns UI + RealityKit/ARKit side effects,
    while gameplay decisions, crowd math, placement scoring, animation sampling,
    parsing, and planning run off-main against immutable snapshots.

MainActor root causes
---------------------
MainActor use is currently driven by four broad constraints:

1. SwiftUI / ObservableObject publication
   - @Published state must be mutated on the main actor.
   - SwiftUI views, gestures, window actions, and immersive-space actions hop to
     MainActor.

2. RealityKit entity graph ownership
   - Entity / ModelEntity creation, parenting, transform mutation, component
     mutation, mesh/material setup, audio emitter placement, and visual debug
     entities are all treated as MainActor-owned in this codebase.

3. ARKit provider/session ownership
   - World tracking, room tracking, plane detection, and hand tracking classes
     are currently MainActor classes. Some provider streams already use async
     loops and then hop back to MainActor for state updates.

4. Historical controller coupling
   - Several controllers combine pure decision logic, state machines, asset
     loading, animation sampling, RealityKit mutation, debug logging, and UI
     callbacks in one @MainActor type. These are the main optimization targets.

Frame loop / runtime path
-------------------------
Current primary frame driver:

1. PlagueImmersiveView.swift
   - Owns a SwiftUI Timer.publish(every: 1/60, on: .main, in: .common).
   - onReceive(frameTimer) calls PlagueImmersiveCoordinator.tick(at:).
   - This means the app's main simulation tick is currently explicitly scheduled
     on the main run loop.

2. PlagueImmersiveCoordinator.tick(at:)
   - Runs on MainActor because PlagueImmersiveCoordinator is @MainActor.
   - Reads current spatial pose from PhaseOneSpatialProvider.
   - Updates room-skinning player pose and wall poster UI.
   - Updates horde room scan.
   - Updates portal ingress controllers.
   - Updates portal FX.
   - Builds crowd snapshots.
   - Calls each JockRetargetTestController.update(...).
   - Applies enemy body separation.
   - Runs debug integrity checks.

3. JockRetargetTestController.update(...)
   - Runs on MainActor because JockRetargetTestController is @MainActor.
   - Updates attack mode.
   - Updates follow movement state.
   - Calls JockRuntimeDriver.update(...).
   - Updates character audio emitter.
   - Updates punch/hit detection.
   - Updates attack damage detection.

4. JockRuntimeDriver.update(...)
   - Runs on MainActor because JockRuntimeDriver is @MainActor.
   - Samples/blends animation clips.
   - Applies active sub-animations.
   - Applies joint transforms to ModelEntity.
   - Applies locomotion root transform deltas through callback.

This is the biggest optimization issue: the main actor owns both the frame clock
and most per-frame computation for every active enemy, every portal FX controller,
collision/steering snapshots, and animation pose application.

High-value off-main candidates
------------------------------
The following are the best first extraction targets because they appear to be
pure math or state transitions currently coupled to MainActor-owned types:

1. Horde crowd + separation simulation
   - Current main work:
     - build crowd snapshots
     - validate enemy body rays
     - decide steer angle
     - solve overlap separation
     - apply corrections
   - Proposed split:
     - MainActor: extract EnemyBodySnapshot values and apply final corrections.
     - Background: CrowdSteeringEngine + BodySeparationSolver.
   - Output: [enemyID: steerAngleDelta], [enemyID: correctionVector].

2. Enemy brain / attack state
   - Current main work:
     - follow/idle/waiting/attack state machine
     - attack anchor logic
     - distance checks
     - damage window timing
   - Proposed split:
     - Background EnemyBrain takes EnemyInputSnapshot + PlayerSnapshot.
     - MainActor applies commands: play walk, play idle, play attack, set transform,
       report damage/death events.
   - Caveat: actual clip playback and joint/entity mutation stay main.

3. JockRuntimeDriver pose sampling
   - Current main work:
     - transition blend
     - pose blend arrays
     - sub-animation overlay
     - locomotion delta extraction
     - joint transform application
   - Proposed split:
     - Background pose sampler returns final joint transforms and root delta.
     - MainActor applies to ModelEntity.
   - This is likely the biggest CPU win if multiple enemies are active.

4. Portal placement and wave planning
   - Current main work:
     - portal creation flow, candidate scoring, assignment, wall/floor/occupancy
       queries, wave spawn sequencing.
   - Proposed split:
     - Background planner consumes value snapshots of room planes, occupancy,
       player pose, wave index.
     - MainActor creates entities/audio only after plan is selected.

5. Portal FX state stepping
   - Current main work:
     - many Entity/ModelEntity pool updates per portal.
   - Proposed split:
     - Background stepper computes transforms/colors/lifetimes.
     - MainActor applies batched diffs to pooled entities.

6. Room skinning / plane processing
   - Current main work:
     - ARKit plane event handling, wall/floor candidate dictionaries, placement
       scoring, poster/door placement.
   - Proposed split:
     - Background geometry reducer maintains candidate values and scores.
     - MainActor applies visible wall/floor/door changes and publishes status.

7. Audio routing
   - Current main work:
     - event selection and RealityKit playback in same large controller.
   - Proposed split:
     - Background audio event router chooses what should play.
     - MainActor audio adapter plays on RealityKit emitters.

Recommended target architecture
-------------------------------

1. MainActor shell layer
   Responsibilities:
   - SwiftUI @Published mutations.
   - RealityKit Entity/ModelEntity creation, parenting, component changes, and
     transform application.
   - ARKit provider/session lifecycle where APIs require main.
   - Audio playback calls on RealityKit entities.
   - GameKit/UI/window calls.
   - Conversion between RealityKit/ARKit live objects and value snapshots.

2. Snapshot layer
   Create explicit value DTOs for all off-main work:
   - FrameClockSnapshot
   - PlayerPoseSnapshot
   - EnemyRuntimeSnapshot
   - EnemyBodySnapshot
   - EnemyAnimationSnapshot
   - RoomGeometrySnapshot
   - PortalRuntimeSnapshot
   - AudioEventSnapshot
   - HordeWaveSnapshot

   Rules:
   - No Entity, ModelEntity, Scene, ARKit provider, ObservableObject, closure, or
     controller references in snapshots.
   - Prefer Sendable structs.
   - Store IDs and primitive math values only.

3. Simulation / planner layer
   Use nonisolated types or actors:
   - HordeSimulationEngine
   - EnemyBrainSystem
   - CrowdSteeringEngine
   - BodySeparationSolver
   - PortalPlacementPlanner
   - PortalFXStepper
   - AnimationPoseSampler
   - RoomGeometryReducer
   - AudioEventRouter

   Inputs: immutable snapshots.
   Outputs: command buffers / diffs.

4. Main apply layer
   Apply command buffers on MainActor:
   - Entity transform diffs.
   - Animation clip commands.
   - Joint transform arrays.
   - Audio commands.
   - UI/session state mutations.
   - Debug draw updates.

Suggested per-frame workflow
----------------------------
Current:

    Main timer -> Main coordinator tick -> every subsystem computes + mutates.

Target:

    Main frame tick
    -> capture minimal snapshots from RealityKit/ARKit/controller state
    -> dispatch snapshot to simulation/planner tasks
    -> main actor continues only essential visual/audio/UI work
    -> collect latest completed command buffer
    -> apply command buffer to RealityKit/ObservableObject state

For real-time gameplay, use last-completed results rather than blocking the main
thread waiting for every background task. It is better to use a one-frame-old
steering/collision result than to stall the main actor.

Risk areas / migration constraints
----------------------------------
- RealityKit Entity/ModelEntity values should be treated as MainActor-owned.
  Do not pass them into background tasks.

- Current enemy snapshots still include controller references:
  HordeEnemyCollisionSnapshot.controller is convenient but prevents safe off-main
  use. Introduce a value-only snapshot before moving collision/steering off-main.

- JockRuntimeDriver currently mutates ModelEntity inside the same method that
  computes pose blending. Split calculation from application before moving work.

- JockRetargetTestController owns too many concerns. Refactor by extracting
  value engines first, then reducing the controller to an adapter.

- The frame timer is on the main run loop. Even after offloading, a main timer is
  acceptable only if it captures/applies quickly.

- Logging is heavy in hot paths. Add throttles or debug-only flags before
  measuring performance. Per-frame print statements can dominate frame time.

- @Published writes in PlagueDemoSession and related ObservableObjects should be
  coalesced. Frequent per-frame publication will invalidate SwiftUI views.

- Asset loading may already use async APIs, but post-load entity setup and
  validation often run in MainActor classes. Keep resource/entity construction on
  main unless verified safe; move parsing/selection/preflight off-main.

Proposed migration order
------------------------

Phase 0: Instrument before changing architecture
- Add timing around:
  - PlagueImmersiveCoordinator.tick
  - updatePortalIngressControllers
  - HordePortalManager.updatePortalFX
  - per-enemy JockRetargetTestController.update
  - JockRuntimeDriver.update
  - body snapshot build
  - crowd steering
  - body separation
  - hit detection
- Track enemy count, portal count, active FX count, and joint count.

Phase 1: Make value snapshots explicit
- Replace controller-containing snapshots with value-only DTOs.
- Add Sendable conformance where practical.
- Keep computation on main initially, but remove Entity/controller references from
  pure math APIs.

Phase 2: Move crowd/separation off-main
- Extract CrowdSteeringEngine and BodySeparationSolver.
- MainActor builds snapshots and applies corrections/steering results.
- This is a low-risk first offload because logic is already mostly math.

Phase 3: Split enemy brain from entity adapter
- Extract follow/attack/lifecycle state into EnemyBrainState and EnemyBrainEngine.
- MainActor controller becomes EnemyEntityAdapter.
- Preserve existing attack behavior through command outputs.

Phase 4: Split animation sampling from pose application
- Create AnimationPoseSampler that consumes prepared clip state and returns final
  transforms/root delta.
- MainActor applies transforms to ModelEntity.
- This is a larger change but likely the biggest per-enemy win.

Phase 5: Portal and FX planners
- Move portal placement/wave planning to a planner actor.
- Move portal FX stepping math off-main and apply batched diffs on main.

Phase 6: Room skinning/ARKit processing
- Convert ARKit streams into small snapshots.
- Move room/wall/floor candidate scoring and occupancy checks off-main.

Definition of "MainActor shell"
-------------------------------
The MainActor shell is successful when:
- PlagueImmersiveCoordinator.tick does not contain domain decisions.
- JockRetargetTestController does not compute brain/crowd/animation math beyond
  snapshot capture and command application.
- JockRuntimeDriver does not blend/sample poses on MainActor, only applies final
  transforms.
- Portal managers do not score/planner-search on MainActor.
- Room skinning managers do not run candidate scoring on MainActor.
- Off-main engines never see RealityKit Entity, ModelEntity, Scene, ARKitSession,
  HandTrackingProvider, WorldTrackingProvider, SwiftUI View, ObservableObject, or
  @Published state.

Immediate architect ticket candidates
-------------------------------------
1. Create TimingProfiler and add scoped timings to the current MainActor tick.
2. Introduce EnemyBodySnapshotValue without controller references.
3. Move HordeCrowdSteering ray validation to pure off-main functions.
4. Move HordeEnemyBodySeparationMath/solve to a pure BodySeparationSolver that
   returns corrections instead of moving entities.
5. Define EnemyCommand and PortalCommand enums.
6. Split JockRuntimeDriver.update into samplePose(...) and applyPose(...).
7. Replace frame log spam in hot paths with throttled debug summaries.
8. Audit @MainActor annotations file by file and remove from pure factories/math
   once signatures are RealityKit-free.
